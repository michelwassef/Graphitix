# Graphitix — Fix studentized-range numerical accuracy and performance

## Objective

Correct the remaining numerical accuracy and performance problems in Graphitix's studentized-range distribution implementation.

The latest audit of the code confirmed that:

1. Studentized-range upper-tail probabilities remain inaccurate, sometimes returning p = 0 for finite, statistically meaningful probabilities.
2. Games–Howell becomes unacceptably slow with increasing numbers of groups, taking approximately 16 seconds for 10 groups (45 comparisons) in a Node.js benchmark.
3. The Games–Howell zero-variance defect identified previously has been corrected and must remain corrected.
4. The broader ANOVA/post-hoc refactor, including method selection, is functioning correctly in the checks performed and must not be reopened unnecessarily.

**This task is a focused numerical correction and optimization, not a redesign of Box statistics.**

Follow `AGENTS.md` strictly. Fix the underlying algorithm, preserve existing architecture and APIs where appropriate, and avoid unnecessary complexity or unrelated modifications.

## 1. Confirmed root cause

The relevant code is primarily in:

`js/shared/boxStatsModel.js`

Investigate:

- `studentizedRangeCDFInfinite`
- `studentizedRangeCDF`
- `adaptiveSimpsonIntegral`
- `resolveStudentizedRangeCritical`
- `computeTukeyComparisons`
- `computeGamesHowellComparisons`
- Other callers, including Nemenyi

The present implementation computes studentized-range probabilities through nested numerical integration.

It calculates upper-tail probabilities using:

```javascript
const cdf = studentizedRangeCDF(q, k, df);
const p = Math.max(0, Math.min(1, 1 - cdf));
```

The current absolute integration tolerance is approximately `1e-7`.

This architecture has two fundamental problems.

**Accuracy:** The numerical integration cannot reliably resolve small upper-tail probabilities. Subtracting an approximate CDF from 1 magnifies relative error and can return zero despite a finite positive probability.

**Performance:** Each finite-df evaluation is expensive. Confidence-interval calculations repeatedly invert the CDF, resulting in many additional nested integrations. Games–Howell is particularly expensive because the pair-specific Satterthwaite degrees of freedom often differ.

Do not address this by simply reducing integration tolerances, increasing iteration counts, clamping probabilities, or caching inaccurate results.

The underlying numerical approach must be replaced or substantially redesigned.

## 2. Required numerical implementation

Implement a scientifically validated, efficient studentized-range distribution calculation suitable for execution in JavaScript, both in the browser and Web Workers.

The solution must provide:

- Accurate survival probabilities, `SF(q, k, df)`.
- Accurate cumulative probabilities, `CDF(q, k, df)`, where required.
- Accurate inverse distribution/critical values.
- Finite positive degrees of freedom, including fractional values.
- Infinite degrees of freedom.
- Integer group counts k ≥ 2.
- Good numerical behavior in extreme upper tails.
- Predictable, bounded execution time.

### 2.1 Algorithm selection

Investigate established numerical algorithms and implementations, including those underlying:

- R `ptukey` and `qtukey`.
- SciPy `scipy.stats.studentized_range`.
- Other independently validated implementations with suitable numerical characteristics.

Evaluate candidate algorithms for:

1. Numerical accuracy across the required domain.
2. Direct or numerically stable upper-tail evaluation.
3. Computational complexity.
4. Convergence reliability.
5. Performance for repeated evaluations.
6. JavaScript/browser compatibility.
7. Licensing compatibility with Graphitix.

Select the simplest maintainable solution that satisfies the accuracy and performance requirements.

Do not blindly port a GPL implementation into Graphitix. Check licenses and document the origin of any adapted mathematical or numerical algorithm.

A numerical algorithm should not be selected merely because it is easy to implement.

### 2.2 Survival-function accuracy

The implementation must avoid the unstable pattern of deriving very small p-values by subtracting an insufficiently accurate CDF from 1.

Prefer a directly evaluated survival probability, a numerically stable complementary formulation, or another validated technique that achieves equivalent accuracy.

Do not disguise numerical error through:

- Arbitrary epsilon floors.
- Artificial minimum p-values.
- Rounding.
- Replacing a failed integration with zero.
- Increasing precision settings without addressing algorithmic limitations.
- Returning a plausible-looking result when convergence has failed.

Use explicit numerical validity/error semantics consistent with Graphitix's existing result contracts.

For mathematically valid finite inputs, p = 0 must not result simply from inadequate quadrature precision.

Distinguish genuine floating-point underflow from failed numerical convergence.

### 2.3 Boundary cases

Test and correctly handle:

| Input                  | Expected behavior                   |
| ---------------------- | ----------------------------------- |
| q = 0                  | CDF = 0, SF = 1                     |
| q = +Infinity          | CDF = 1, SF = 0                     |
| Finite positive q      | Valid distribution probability      |
| df = +Infinity         | Correct infinite-df limit           |
| Positive fractional df | Supported                           |
| Invalid df             | Unavailable/error, not fabricated p |
| Invalid k              | Unavailable/error                   |
| NaN                    | Unavailable/error                   |

The previous implementation incorrectly returned CDF = 0 for q = +Infinity. Correct this at the distribution boundary.

Ensure monotonicity:

- CDF must be nondecreasing with q.
- SF must be nonincreasing with q.

## 3. Optimize computation without compromising correctness

The updated algorithm must be substantially faster than the existing nested integration.

The previously measured performance was approximately:

| Games–Howell | Existing runtime |
| ------------ | ---------------: |
| 3 groups     |           495 ms |
| 5 groups     |         3,890 ms |
| 10 groups    |        16,287 ms |

These figures were measured in Node.js and are reference baselines, not universal hardware-independent timings.

### 3.1 Performance targets

The corrected implementation should:

- Provide at least an order-of-magnitude speedup for representative multi-group workloads, where feasible.
- Aim to complete a 10-group Games–Howell analysis in under one second in the comparable Node.js test environment.
- Remain responsive for 25 groups (300 comparisons).
- Avoid long synchronous calculations blocking the browser UI.
- Maintain acceptable performance for small/fractional df and extreme tails.

Treat these as performance goals to verify, not as justification for inaccurate approximations.

If a target cannot be achieved without sacrificing numerical reliability, investigate alternative algorithms and report the measured tradeoff.

### 3.2 Critical-value computation

Pay particular attention to `resolveStudentizedRangeCritical`.

The existing repeated CDF inversion is a major source of computational expense.

Use an efficient, convergent root-finding procedure compatible with the new probability evaluator.

Prefer solving the survival-function equation directly for upper-tail critical values when numerically advantageous:

`SF(qCritical, k, df) = alpha`

Use a mathematically valid bracket and a bounded convergence criterion.

Avoid unnecessary distribution evaluations.

For Tukey, reuse a critical value when all comparisons share the same k, df, and confidence level.

For Games–Howell, recognize that individual pairs have different df. Optimize the underlying algorithm rather than relying on caching alone.

### 3.3 Caching

Only introduce caching where profiling demonstrates a meaningful benefit.

If used:

- Cache only deterministic numerical results.
- Key caches by all relevant parameters.
- Keep caches bounded.
- Do not introduce mutable per-tab statistical state.
- Do not cache failed or insufficiently accurate evaluations as valid results.

Correctness must never depend on a previous computation having populated a cache.

### Games–Howell

- Pair-specific sample variances.
- Welch-style standard errors.
- Satterthwaite degrees of freedom.
- Games–Howell q-statistics.
- Intrinsic multiple-comparison correction.
- Simultaneous confidence intervals.

**Do not regress the recently corrected zero-variance behavior.**

In particular:

- A group with exactly zero variance must retain variance = 0.
- A zero-variance group paired with a positive-variance group can yield a valid comparison.
- A pair with zero combined variance must be rejected appropriately.
- Never replace real zero variances with `Number.EPSILON`.

### Nemenyi and other consumers

Audit all callers of the current studentized-range functions.

Ensure that nonparametric post-hoc approximations continue to use the correct distribution and scaling conventions.

Do not change exact or permutation-based nonparametric procedures unnecessarily.

### Unrelated statistical methods

- Welch ANOVA.
- ANOVA-pooled pairwise t-tests + Holm.
- Independent Student/Welch pairwise t-tests.
- Other multiplicity corrections.
- Unrelated parametric and nonparametric tests.

Do not modify method defaults, statistical advisor decisions, or method-selection behavior.
